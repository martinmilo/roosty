## The problem this record serves

Record 1 reads `.roosty/`; nothing yet creates it. On the trial project the folder, the scan output and the
instruction to the agent were all made by hand. `init` starts a project and prints what an
agent needs in order to fill it. `scan` turns the project's own knowledge of its entrypoints
into `entrypoints.tsv`.

## Decided

### `roosty scan`

- `.roosty/scan` is an executable file the project owns, written in any language. Roosty
  runs it directly, with the repository root (the folder that holds `.roosty/`) as its
  working directory, and reads its stdout. This is how Git runs a hook: an executable at a
  known path, started from the root of the working tree.
- The script prints a `# covers:` line naming the kinds it looks for, then one row per
  entrypoint: `kind`, `name`, `file` and optionally `area`, separated by tab characters.
- Roosty checks the output, sorts the rows by their full line in byte order, and writes
  `.roosty/entrypoints.tsv` with the `# covers:` line first. It writes nothing else.
- `scan` is the only command that runs repository code. The overview, `show`, `validate` and
  `init` never run `.roosty/scan`.

**Proposed**, what roosty tidies while writing:

- The `# covers:` line is written by roosty with the kinds in the closed list's order,
  separated by single spaces, whatever order the script named them in. The file is then the
  same for the same entrypoints, however the script is arranged.
- A row whose fourth column is empty is written as a three-column row. A script that joins
  four values with tabs prints a trailing tab for every entrypoint without an area; that is
  the most likely script an agent writes, and the file may not have trailing tabs.

**The report**, on stdout, exit 0. **Proposed** layout:

```
+ http POST /waiting_list
+ job WaitingListJob
- mail BookingMailer#reminder

8 entrypoints, 2 added, 1 removed
```

- An entrypoint is its `<kind> <name>`. Added entrypoints are listed first, then removed
  ones, each group in the file's sort order. A row whose file or area changed is neither
  added nor removed; the file is still rewritten.
- The last line is always `<n> entrypoints, <a> added, <r> removed`. When nothing was added
  or removed it is the only line: `7 entrypoints, 0 added, 0 removed`.
- A first scan, with no previous `entrypoints.tsv`, lists nothing and prints
  `<n> entrypoints, first scan`. No previous file is not the same as an empty one, and on
  the trial project the alternative is 93 lines beginning with `+`.

**Could not run**, exit 2, reason on stderr, nothing written:

- No `.roosty/project.yml`: says to run `roosty init`, as every command does.
- No `.roosty/scan`: names `.roosty/scan` and says it must be an executable that prints the
  entrypoints.
- **Proposed**: `.roosty/scan` exists but is not executable: names the file and gives
  `chmod +x .roosty/scan`. Git ignores a hook that is not executable and prints a hint;
  roosty was asked to scan, so it refuses instead of ignoring.

**Refused**, exit 1, reasons on stderr, `entrypoints.tsv` left exactly as it was, and not
created when it did not exist:

- The script exits non-zero, even when what it printed is well formed. The reason gives the
  exit code. Whatever the script wrote to its own stderr is passed on, so the cause is
  visible.
- What the script writes to stderr is passed on to roosty's stderr whenever it runs, and is
  never by itself a problem: a script that prints a deprecation warning and exits 0 has
  succeeded. (Added on confirmation, scenario 95.)
- The output is malformed. Every problem is reported, one per line, as
  `line <n>: <problem>`, where `n` is the line of the script's output starting at 1. All
  problems are reported in one run, as `validate` does. Malformed means any of:
  1. the first line is not a `# covers:` line;
  2. the `# covers:` line names a kind outside the closed list;
  3. a row has fewer than three or more than four columns;
  4. a row's kind is outside the closed list;
  5. a row's kind is not named on the `# covers:` line (the overview would otherwise show
     the kind both counted and `not scanned`);
  6. a row's kind, name or file is empty;
  7. two rows have the same kind and name. A process refers to an entrypoint by kind and
     name, so that pair has to identify one row.

  Rules 5 to 7 are **proposed**; the brief said "malformed rows".

### `roosty init`

- Creates `.roosty/project.yml`, the starter below, and nothing else. It does not create
  `.roosty/scan` or `processes/`, and it never edits `AGENTS.md`; it prints the line for a
  person or an agent to add.
- Never overwrites. When `.roosty/project.yml` exists it is left as it is and reported.
- **Proposed**: one status line per file, `create  <path>` or `exists  <path>` (two spaces),
  the form `rspec --init` and the Rails generators use.
- **Proposed**: exit 0 both times, and the line for `AGENTS.md` and the setup instruction are
  printed both times. `git init`, `terraform init` and `rspec --init` all succeed when run
  again; and running `init` again is the only way to get the instruction back when a setup
  was left half done.
- **Proposed**: the starter's `name` is the name of the folder `init` runs in, as
  `npm init -y` and `cargo init` do. Every other key is a commented example, so the starter
  passes `validate` as written and shows nothing that is not known.
- `init` needs no test handle. Tests that depend on the folder's name give the test's folder
  a name.

The starter `.roosty/project.yml`, for a folder called `pottery-studio`:

```yaml
# What roosty shows about this project. Read it with `roosty`, check it with
# `roosty validate`. Remove the "# " in front of a key to use it.
name: pottery-studio

# The stack, one line.
# stack: Rails 8, PostgreSQL, Solid Queue

# What the project is for, one sentence.

#     command: bin/deploy

# Where the project runs, one line each.
# environments:
#   staging: staging.example.com
#   production: example.com
```

### What `init` prints

```
create  .roosty/project.yml

AGENTS.md
Add this line to AGENTS.md, so that agents read the overview before they work
on the project:

When you need to understand this project's functionality, structure, or recent changes, run `roosty` for the project overview. Use `roosty show <id>` to inspect a specific process before modifying its behavior.

SETUP
Give this instruction to an agent working in the repository, or follow it
yourself.

Set up roosty for this project. Do the steps in order. Where something cannot
be established from the code or from the owner, write "unknown". Never guess.

1. Write the scan script first.

   Create .roosty/scan and make it executable. It may be written in any
   language. The script must only read. It must not write files, change a
   database or call the network. roosty runs it from the repository root and
   reads what it prints:

     # covers: http job mail
     http<TAB>POST /orders<TAB>app/controllers/orders_controller.rb<TAB>Orders
     job<TAB>ReceiptJob<TAB>app/jobs/receipt_job.rb<TAB>Orders
     mail<TAB>OrderMailer#receipt<TAB>app/mailers/order_mailer.rb

   The first line names the kinds the script looks for, out of http, job,
   mail, schedule, event and cli. Every other line is one entrypoint: kind,
   name, file and area, separated by one tab character each, shown above as
   <TAB>. The area is the part of the project the entrypoint belongs to, such
   as a controller namespace, an app or a folder. It may be left off a row,
   but give every http row an area. Take the list from the framework (its
   routes command, its job and mailer classes), not from reading files by
   hand.

   Run `roosty scan` and correct the script until it succeeds. It writes
   .roosty/entrypoints.tsv, which is never edited by hand.

2. Fill in .roosty/project.yml.

   The comments in the file describe each key. Keep watch_out to what someone
   must know before touching the project at all. What concerns one behaviour
   belongs in that behaviour's record.

3. Describe the three most important behaviours first.

   Each behaviour is one file, .roosty/processes/<id>.yml, and the file name
   is its id. Only name and description are required:

     name: Place an order
     group: Orders
     description: Take a paid order and mail the receipt.
     entrypoints:
       - http POST /orders
       - job ReceiptJob
       - mail OrderMailer#receipt
     files:
       - path: app/models/order.rb
         note: holds the order states
       - app/services/place_order.rb
     try: |
       Put a mug in the basket and pay with card 4242 4242 4242 4242.
       Check the receipt in the mail preview.
     outcomes:
       paid:
         when: the payment succeeds
         then: the order is saved and the receipt is mailed
       declined:
         when: the card is declined
         then: nothing is saved
     why:
       - Stock is reserved only after payment, so an abandoned basket holds
         nothing back.

   Set group to the area of the process's main entrypoint, spelled as in
   entrypoints.tsv. Under entrypoints, list every entrypoint the behaviour
   starts from or runs through (the request that starts it, the jobs it
   enqueues, the mails it sends), each written as its kind and name. Keep
   each line of try to 69 characters; it is printed as written. Read each
   record back with `roosty show <id>`.

4. Finish with `roosty validate`.

   Correct every finding until it prints "No problems found". Then run
   `roosty` and read the overview as someone new to the project would.

Stop here. Tell the owner what you could not establish and which areas have no
process yet, and let them choose what to describe next.

Do not commit. The owner reviews .roosty/ first.
```

Changed on confirmation: step 1 says the script must only read (no files written, no
database changed, no network called); step 3 limits a line of `try` to 69 characters, the
room `show` leaves after its label column; after step 4 comes "Stop here" with what to tell
the owner; the instruction closes with "Do not commit". The draft left open what follows the
first three behaviours; the owner decided that the agent stops and the owner chooses.

The "stop" paragraph first sat at the end of step 3, worded "Then stop". An agent could have

Where each lesson from the trial sits: scan script first and `roosty scan`, step 1; an

### validate

- The same entrypoint listed twice in one record is a finding. It names the record, the
  entrypoint and the position of the repeat. The same entrypoint in two different records is
  not a finding: a mail sent by two behaviours belongs in both.
- A finding names an item of a list by its position starting at 1. **Proposed** form: the
  position is one more step of the dotted path, `watch_out.2`, `entrypoints.3`,
  `files.2.note`. Square brackets are avoided because `[2]` reads as the third item to
  anyone used to jq, JSONPath or Kubernetes messages. This closes the question record 1b
  left open.

## Test kit

- A failed exact-text comparison (`assert_stdout_is`, `assert_file ..., is:`) now shows the
  expected text line by line, each line marked `missing` or `remove`, with a tab drawn as an
  arrow and quotes unescaped. The texts of this record contain quotes, tabs and lines that
  start with `+` and `-`, which the old diff rendered ambiguously.
- A helper can add a note to the transcript of a failure (`note_situation`). The fake scan
  scripts use it, so a failure shows what `.roosty/scan` printed and how it exited.
- New words: `scan`, `init`, `scan_prints`, `scan_script`, `folder_named`,

## Left out of this record
