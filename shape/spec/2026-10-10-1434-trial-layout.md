# Record 1a: layout after the trial on a real project

Date: 2026-10-10. Supersedes the layout and file-format sections of
`2026-10-10-1304-overview-show-validate.md` (record 1). Everything in record 1 that this
record does not mention still stands: the three commands, exit codes, the closed list of
kinds, the `<kind> <name>` reference form, the validate checks, the Atelier fixture.

The trial ran the overview on a real project (the trial project, 93 entrypoints). Five changes came back,
all about layout and the input formats that feed it. With the layout settled, the two frozen
screens (scenarios 1 and 14) are written in this record.

## Decided

### `project.yml` gains two keys

- `description`: one sentence, printed under the title line, wrapped at 80. Optional.
- `watch_out`: a list of sentences, printed as a WATCH OUT section directly under the
  description, one item per line, indented two, wrapped at 80 with the continuation aligned.
  Left out when the list is missing or empty.
- Each operation is a command plus an optional note. An operation's value is either the
  command as a string, or a map with `command` and `note`. The note is printed on the same
  line, after the command.

### `entrypoints.tsv` gains an optional fourth column, `area`

A row has three or four tab-separated columns: `kind`, `name`, `file`, and optionally
`area`. Rows may mix three and four columns in one file. `validate` accepts both.

### The overview, `roosty`

The separate ENTRYPOINTS section and the "n of m entrypoints are not described" line are
gone. FUNCTIONALITY now carries both roles.

```
<name>                                                      <stack, right-aligned to 80>
<description, wrapped at 80>

WATCH OUT
  <sentence>
  <sentence>

FUNCTIONALITY                                    <total> entrypoints, <n> described
  <Area>             <kind> <n>   <kind> <n>
    <process-id>       <description, one line>
  <Area>             <kind> <n>
  other              <kind> <n>
    <process-id>       <description>
  none found: <kinds>   not scanned: <kinds>

WORK WITH THIS PROJECT
  <operation>     <command>   <note>
  <environment>   <where it runs>

NEEDS ATTENTION
  <file>   cannot be read, run roosty validate
```

Rules:

- The FUNCTIONALITY heading carries `<total> entrypoints, <n> described` right-aligned to
  column 80, where `total` is the number of rows in `entrypoints.tsv` and `described` the
  number of them that at least one process lists. Without `entrypoints.tsv` the heading
  carries `not scanned yet` instead. FUNCTIONALITY is always shown; with no processes and
  no `entrypoints.tsv` it is the heading line alone.
- An area is a value of the fourth column. Every area is listed, in alphabetical order, even
  when no process belongs to it. Its line shows the area name, then one `<kind> <n>` per
  kind that has entrypoints in that area, in the closed list's order, zero counts left out.
- A process is listed under the area named by its `group`. A `group` that is not an area
  still gets its own line, in the same alphabetical order, with no counts.
- After the areas comes a line labelled `other`. It shows one `<kind> <n>` for each kind
  that has entrypoints with no area, in the closed list's order, zero counts left out, so it
  never looks as if the project lacks a kind it has. Processes without a `group` are listed
  under it. The line is left out when there are no entrypoints without an area and no
  processes without a group. (Changed 2026-10-10 before implementation started: the first
  version showed every covered kind with zeros, which read as "this project has no http".)
- The last line of the block is the coverage line: `none found: <kinds>` for kinds the scan
  covers but found nowhere in the project, then `not scanned: <kinds>` for kinds the scan
  does not cover, the two halves separated by three spaces. Either half is left out when
  empty, and the whole line when both are. Indented two, no label column.
- The area column (areas and `other`) is as wide as the longest label shown plus three
  spaces, indented two. The id column is as wide as the longest id shown plus three spaces,
  indented four. A description is cut so its line does not pass column 77; a cut
  description ends in `...`, with any space before the dots removed.
- WORK WITH THIS PROJECT: the label column is as wide as the longest label plus four
  spaces. A note follows its command in a column as wide as the longest command shown plus
  three spaces. A line without a note has no trailing spaces. A command or note is never cut;
  the line may pass column 80.
- Wrapping everywhere is greedy on spaces: a line takes as many whole words as fit.

### One process, `roosty show <id>`

```
<id>   <name>                                                <Group, right-aligned>
<description, wrapped at 80>

  entry    <kind> <name>
           <file from entrypoints.tsv, or: not in entrypoints.tsv>
  code     <path>                    <note>
           <path>
  try      <first line as written>
           <next line as written>

OUTCOMES
  <outcome>   <when>: <then, wrapped with the continuation aligned under the text>

WHY
  <first item, wrapped at 80>

  <second item, wrapped at 80>
```

Rules:

- Each entrypoint takes two lines: the reference, then its file from `entrypoints.tsv`
  aligned under it, or `not in entrypoints.tsv` when the scan did not find it.
- `files` items are either a path as a string or a map with `path` and `note`. The note
  follows the path in a column as wide as the longest path shown plus three spaces.
- `try` is multi-line text printed as written, every line aligned under the first; no
  wrapping, no cutting.
- `why` is a list. Each item is its own paragraph, wrapped at 80 with an indent of two,
  paragraphs separated by one blank line.
- Outcome text wraps at 80, continuation lines aligned under the start of the text.
- The label column (`entry`, `code`, `try`) is nine wide after an indent of two, so text
  starts at column 12 and continuation lines are indented eleven.

### Validate

Unchanged, except that an `entrypoints.tsv` row may have three or four columns, and
`project.yml` values for operations and `files` items may be strings or maps as above. A
`why` that is not a list, or a `watch_out` that is not a list, is a finding.

## Added in the test review of 2026-10-10

- **A `group` that matches no area** is listed under its own heading with no counts, in the
  same alphabetical order as the areas. Groups are written by hand and areas come from the
  scan, so they will often differ. (Already a rule above; now scenario 40 and a test.)
- **A `project.yml` that does not parse.** The overview and `show` exit 2, name the file
  and point at `roosty validate`. `validate` reports it as a finding and still checks the
  process records. This refines record 1, where only a missing `project.yml` was covered.
- **A key with the wrong shape** is a `validate` finding naming the file and the key: for
  example `why` given as a single string instead of a list, or `watch_out` given as a
  string. Every key in FORMATS.md has one shape and `validate` enforces it.
- **Test renamed.** "In a folder that is not a Git repository, LAST 7 DAYS and NEEDS
  ATTENTION are left out" contradicted the unreadable-record test, which needs NEEDS
  ATTENTION in a folder without Git. It now says LAST 7 DAYS is left out, and NEEDS
  ATTENTION is left out when no record is unreadable.
